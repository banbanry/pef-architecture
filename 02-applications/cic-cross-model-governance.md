## 序言：体系闭环——π 回到正中央

本文档是 PEF-CIC 架构的第五份文档，也是 π 锚点体系的第三应用。此前在跨模型代码协作场景的设计中，我曾犯了一个方向性错误——将代码协作场景降格为「轻量剥离形态」（YAML 契约 + ESLint + CI 门禁），把 π 悄悄换成了「结构锚」，把账本拿掉了。这一降格违背了架构的核心设计意图：PEF-CIC + π 不是绕过架构走捷径，而是在第三个场景完整建制运行——这才叫体系闭环。

本文档纠正这一方向错误。π 回到正中央，PEF 四层（P-E-F-M）全建制进场，StateLedger 账本、LOCKED 机制、哈希链、公理常量验签、D-S 调度 λ 全部保留。跨模型代码协作不是「轻量 CI 方案」，而是 PEF-CIC 架构在空间轴上的完整部署——与会话场景（时间轴）形成同一架构的两次部署。

核心洞察：方言偏差就是「空间化的公理漂移」。会话场景的公理软性漂移是时间轴上的契约失守（第 80 轮忘了第 3 轮的契约），代码协作场景的方言偏差是空间轴上的契约失守（模型 B 不知道模型 A 的隐式约定）。两者是同一个病理在两个正交维度上的投影，因此答案是同一个架构的完整复用，而非发明新机制。

本文档的模拟实施例使用 GLM 5.3 / 4.0 / 3.0 三个版本接力开发一个项目，展示 π 锚点如何将三个版本的代码方言收敛到统一契约之下。这一模拟既是架构验证，也是 GLM 团队合作的参考案例——展示 PEF-CIC 能为多模型协作带来什么。

## 第一部分　理论基础

### 第一章　方言偏差 = 空间化的公理漂移

这是整个重设计的核心洞察，先把统一理论立起来。PEF-CIC 架构治理的病理本质是「契约锚点在产出侧的失守」。这一病理在两个正交维度上有两个投影：

两个场景是同一个病理在两个正交维度上的投影。所以答案不是发明新机制，而是完整复用现有架构——π 在时间轴上是时序盐值（防轮次漂移），在空间轴上变成实体锚（防模型间方言漂移）。体系由此闭环：一个架构，治理契约漂移的两个轴。

这一统一理论的意义在于：它将「跨模型代码协作」从「需要新工具的新问题」重新定义为「已有架构的新部署」。所有为会话场景设计的机制（π 锚、StateLedger、LOCKED、探针、D-S 调度）在代码协作场景中直接复用，只是参数语义变化——「轮次」换成「模块」，「P 层单模型多轮」换成「P 层多模型接力」。这就是体系闭环的字面意义：同一套时序图，参数换了，逻辑一行不改。

### 第二章　两层标准：语法标准 vs 工程行为标准

要理解 AI 代码方言的根源，必须先分清两层标准。第一层是底层语言标准（ISO/JDK/PEP-8）——这是表层句法规则，所有模型都遵守。C 语言 ISO 标准、Java JLS、Python PEP-8 规定了变量怎么声明、循环怎么写、函数参数格式、关键字。DeepSeek、GLM、Trae 基本不会写出非法语法。这一层不会产生方言偏差。

第二层是工程隐性契约——这一层没有官方强制标准，完全靠开发者/AI 自己的习惯决定，也是跨模型拼接 90% 隐性 Bug 的发源地。这就是 AI 代码方言的来源：每个模型在训练数据中见过不同的工程范式，生成了不同的「工程文化习惯」。语法标准只规定「句子怎么写」，没有规定「故事怎么分段、角色怎么分工、出错了怎么办」。

关键结论：语法标准 ≠ 工程实现标准。C/Java 只规定「句子怎么写」，没有规定「故事怎么分段、角色怎么分工、出错了怎么办」。AI 方言 = 各个模型训练集学到的不同「工程文化习惯」。PEF-CIC + π 锚点治理的是第二层——工程行为标准，而非第一层语法标准。

### 第三章　AI 代码方言的四大指纹

AI 代码方言分为四大类指纹，每一类都是跨模型拼接隐性 Bug 的发源地：

#### 3.1　架构分割指纹（模块边界方言）

同样一个功能模块，三个模型切分思路不一样。DeepSeek 喜欢大函数、少文件、高内聚，业务逻辑塞在 controller；GLM 喜欢超薄控制器、全部下沉 Service 层、拆成极小函数；Trae 喜欢自动拆出一堆中间 DTO、适配器、helper 工具类。底层架构目标一致，但模块边界契约不一致。拼到一起就出现：有的类职责重复、有的链路悬空、依赖方向反转。语法完全合法，运行时逻辑断层。

#### 3.2　错误处理指纹（异常方言）

没有强制标准时，每个模型有一套本能习惯。DeepSeek 大量裸 try-catch，吞异常不打印日志；GLM 偏好自定义异常枚举，每层向上抛；Trae 到处返回 Result<T> 包装，极少抛异常。三份代码合并，会出现异常链路断裂，报错消失、静默失败。

#### 3.3　状态与副作用指纹（最隐蔽的隐性 Bug）

同一个全局状态、缓存、上下文对象：A 模型认为调用后会修改传入对象；B 模型认为函数只读，不会修改入参；C 模型新建副本再修改。语法全部合法，但是隐式约定冲突，并发、时序一乱就崩。这就是典型「隐性兼容性 Bug，编译查不出来，单元测试很难覆盖」。

#### 3.4　命名、回调、生命周期、资源释放方言

回调函数传参顺序、线程池关闭策略、数据库事务边界、锁粒度——语言标准完全不管这些，每个模型训练数据里见过不同工程范式，就生成不同风格。

【公式闭环】第一部分 公式闭环

统一理论: 方言偏差 = 空间化公理漂移，同病同方同治。

两层标准: 语法标准（ISO/JDK/PEP-8）所有模型遵守；工程行为标准（无官方强制）= AI 方言来源。

四大指纹: 架构分割 / 错误处理 / 状态副作用 / 命名回调生命周期。

治理目标: 第二层工程行为标准，非第一层语法标准。

体系闭环: 同一架构两次部署，参数换（轮次→模块），逻辑不改。

## 第二部分　π 在代码场景的三重角色

在会话场景中，πₛ 承担双重角色：分域映射（pi%3 → domain）与审计链盐值（驱动 λ）。在代码协作场景中，πₛ 扩展为三重角色——新增「实体锚」这一核心用法。三重角色共同构成 π 在空间轴上的完整治理能力。

### 第四章　实体锚——π 的核心新用法

实体锚是 π 在代码场景的核心新用法。每个接口、每条契约、每个通过审计的模块，在诞生时从 πₛ 序列领取唯一锚号。StateLedger 记录绑定关系：

πₛ → 实体哈希 → 分配时间 → 实现模型 → 审计探针版本

（式 4.1）

实体锚的分配规则与会话场景完全一致：递增分配、禁止跳号、禁止复用。每个 LOCKED 实体（接口定义、契约条目、通过审计的模块）在 StateLedger 中有一条记录，包含 πₛ 锚号、实体内容哈希、分配时间戳、实现模型标识、审计探针版本号。

实体锚的工程意义：它为跨模型引用提供了确定性锚点。当 GLM 4.0 实现模块 B 时，它引用 GLM 5.3 实现的模块 A 的接口——这一引用必须指向模块 A 的 πₛ 锚号，而非模块 A 的文件名或路径。锚号是唯一的、不可复用的、不可篡改的（篡改会导致哈希链断裂）。这使得跨模型引用从「靠文件名约定」升级为「靠数学锚号绑定」，消除了文件名冲突、路径漂移、版本混淆等隐性 Bug。

### 第五章　分域映射——pi%3 → domain 三域

pi%3 → domain 的三域映射在代码场景中承载不同的内容，但映射规则与会话场景完全一致：

注意审计域的分量：没有 π 分域，Trae 打包时就能顺手「优化」一下探针规则——这是轻量方案（纯 CI）的结构性漏洞。π 分域将审计域对全部 P 节点（包括 Trae）设为只读，任何 P 节点都无法修改探针规则来放行自己。这是「谁审计审计者」问题的结构性答案。

### 第六章　时序盐值——防模型预测审计序列

时序盐值在代码场景中防模型预测审计序列。探针对同一接口在不同审计轮次产生不同哈希偏移，知晓探针逻辑的模型也无法构造恰好落在检测边界外的产出。

H_n = SHA-256(H_{n-1} || πₛ || n || entity_hash || probe_version)

（式 6.1）

其中 πₛ 是该实体的锚号，n 是审计轮次序号，entity_hash 是实体内容哈希，probe_version 是探针版本号。由于 πₛ 对每个实体唯一，且 n 随审计轮次递增，即使两个实体的内容完全相同（如同一接口被两个模型实现），其哈希也不同。这使得模型无法通过「记住探针的检测边界」来构造恰好绕过的产出——每次审计的哈希偏移都不同。

这一时序对抗机制对应 CLE（编程场景）中的 π 时序对抗思想：π 不仅做静态分域，还做动态时序盐值，防止模型在长会话或多次审计中学习探针模式。

【公式闭环】第二部分 公式闭环

π 三重角色: ①实体锚（唯一锚号绑定）+ ②分域映射（pi%3→domain）+ ③时序盐值（防预测）。

实体锚: πₛ → 实体哈希 → 分配时间 → 实现模型 → 探针版本，递增/禁跳号/禁复用。

分域映射: 业务域（实现模块）/ 审计域（只读）/ 降级域（隔离），审计域对全部 P 节点只读。

时序盐值: H_n = SHA-256(H_{n-1} || πₛ || n || entity_hash || probe_version)，防预测。

体系闭环: 三重角色共同构成 π 在空间轴的完整治理能力。

## 第三部分　四层完整映射

本部分展开 P-E-F-M 四层在代码协作场景的完整映射。核心设计决策：Trae 也是被审对象，不是审计者。这一决策回应了「谁审计审计者」问题——Trae 是权力最大的节点（唯一能碰全部代码），因此更不能让它掌握审计权。

### 第七章　P 层：分布式策略生成（Trae 也是被审对象）

P 层在代码协作场景中是分布式策略生成层，由多个模型节点组成。每个节点只负责一个封闭子模块，无最终决策权。关键设计：三个模型之间禁止直接交换产物。

P 节点隔离原则：三个模型之间不许直接 import 对方的内部实现。所有跨模型引用必须落在 LOCKED 接口库上——引用非 LOCKED 的实体（无论接口还是模块）= 结构级探针直接 FAIL。这一条同时防无意的方言污染和有意的私下串供。

### 第八章　M 层：采集 + Schema 校验 + StateLedger

M 层在代码协作场景中承担四大职责：

第一，无偏向采集：抓取每个 P 节点的代码产出、工具调用、中间产物，形成原始证据流。第二，Schema 证据校验：入账前执行轻量本体 Schema 校验，证据必须携带 Source_Ref（哪个模型/哪个 πₛ/文件哈希）；不合规证据降权/拒收。第三，StateLedger 维护：维护 πₛ 实体锚分配记录，账本仅允许追加，禁止原地改写。第四，哈希链防篡改 + LOCKED 锁定：F-PASS 后写入 LOCKED 标记，附带审计哈希、探针版本号。

Source_Ref 在代码场景的强制字段：

Source_Ref = {
    model_id: "GLM-5.3",        // 实现模型标识
    pi_anchor: 14159,          // πₛ 实体锚号
    file_hash: "a1b2c3d4...",   // 文件内容哈希
    timestamp: "2026-08-25T10:30:00Z",
    probe_version: "v1.2.0"     // 审计探针版本
}

### 第九章　E 层：上下文编排 + AST/LTL 冲突检测

E 层在代码协作场景中承担两大工作：上下文编排与形式化冲突检测。核心铁律不变：E 层只允许检测、编排、否决、发切换信号，禁止编辑/修正 P 层输出内容。

上下文编排是方言治理的第一道闸：给 DeepSeek 注入的系统提示里带完整的异常处理契约 + 已 LOCKED 接口清单——前置引导（生成时就锚定）与后置审计（产出后探针拦截）双保险，退回重写率大幅下降。E 层将锚点契约 + LOCKED 接口清单注入目标模型上下文，使得模型在生成时就遵循统一契约，而非生成后再被拦截。

形式化冲突检测：E 层读 M 证据流做 AST（抽象语法树）解析与 LTL（线性时序逻辑）冲突检测。AST 解析检查模块边界、接口签名、依赖方向是否符合锚点契约；LTL 检查时序约束（如资源生命周期、事务边界）是否被违反。检测到冲突直接否决，返回 P 层重生成——E 无修改权，不能「顺手修正」。

### 第十章　F 层：π-锚探针三层布尔审计 + D-S 调度

F 层在代码协作场景中保持修复后的结构：主裁决路径是 π-锚探针布尔审计（一票否决），D-S 证据融合退化为调度辅助路径（只调 λ，不参与单轮放行）。

主裁决路径（不可操纵、可硬件化）：π-锚探针三层布尔审计。第一层结构级探针：检查分层、目录、接口签名是否违背锚点（布尔裁决 PASS/FAIL），包括哈希链完整性、常量签名校验、LOCKED 引用检查、π-domain 单向映射检查。第二层语义级探针：扫描副作用、异常处理模式（依赖 AST 符号翻译，存在翻译鸿沟漏报风险）。第三层行为级探针：代码风格、命名习惯（仅信号，不拦截）。

调度辅助路径（概率统计，不参与单轮放行/阻断）：D-S 证据融合。跨模型违规频次统计（DeepSeek 的 EH 域高发、GLM 的 AR 过度拆分、Trae 的 DTO 泛滥）累积成指纹库 → 对应模型交付时对应域探针自动加严。注意铁律不变：D-S 只调 λ，不参与单轮放行——方言统计决定「审多严」，不决定「过不过」。

【公式闭环】第三部分 公式闭环

P 层: 分布式策略生成，Trae 也是被审对象，三模型禁止直接交换产物。

M 层: 采集 + Schema 校验（Source_Ref 必填）+ StateLedger + 哈希链 + LOCKED。

E 层: 上下文编排（锚点契约注入）+ AST/LTL 冲突检测，无修改权。

F 层: π-锚探针三层布尔审计（主裁决）+ D-S 调度 λ（辅助，不参与放行）。

谁审计审计者: Trae 整合产物再走 M-E-F 全链路，审计域对全部 P 节点只读。

## 第四部分　完整工作时序

### 第十一章　十步工作流（复用会话场景）

修复后的工作时序复用会话场景的十步结构，每一步结构同构，只是「轮次」换成了「模块」，「P 层单模型多轮」换成了「P 层多模型接力」。这就是体系闭环的字面意义——同一套时序图，参数换了，逻辑一行不改。

### 第十二章　四条关键设计

#### 12.1　P 节点隔离

三个模型之间不许直接 import 对方的内部实现。所有跨模型引用必须落在 LOCKED 接口库上——引用非 LOCKED 的实体（无论接口还是模块）= 结构级探针直接 FAIL。这一条同时防无意的方言污染和有意的私下串供。

#### 12.2　Trae 的权力被关进笼子

这是轻量方案最致命的缺陷所在。在轻量 CI 方案中，Trae 做「打包整合 + 跑审计」，等于让权力最大的节点（唯一能碰全部代码的）同时掌握审计权。谁审计审计者？PEF 架构给出结构答案：Trae 也是 P 节点，它的整合产物同样过 M-E-F 全链路，探针和账本在审计域，它碰不到。

#### 12.3　E 层上下文编排是方言治理的第一道闸

给 DeepSeek 注入的系统提示里带完整的异常处理契约 + 已 LOCKED 接口清单——前置引导（生成时就锚定）与后置审计（产出后探针拦截）双保险，退回重写率大幅下降。这一前置引导是 PEF-CIC 区别于纯 CI 方案的关键——CI 只做事后拦截，PEF-CIC 做事前引导 + 事后拦截双保险。

#### 12.4　D-S 调度 λ 完整进场

跨模型违规频次统计（DeepSeek 的 EH 域高发、GLM 的 AR 过度拆分、Trae 的 DTO 泛滥）累积成指纹库 → 对应模型交付时对应域探针自动加严。注意铁律不变：D-S 只调 λ，不参与单轮放行——方言统计决定「审多严」，不决定「过不过」。

【公式闭环】第四部分 公式闭环

十步工作流: 会话场景与代码场景结构同构，参数换（轮次→模块），逻辑不改。

P 节点隔离: 三模型禁止直接交换产物，跨模型引用必须落在 LOCKED 接口库。

Trae 被审: 整合产物再走 M-E-F 全链路，审计域对 Trae 只读。

E 层双保险: 前置引导（契约注入）+ 后置审计（AST/LTL 检测）。

D-S 调度: 方言频次统计 → 指纹库 → λ 自动加严，不参与放行。

## 第六部分　探针系统设计

### 第十八章　探针设计原则

PEF-CIC 探针系统遵循四组原则：有效性原则、结构性原则、工程化原则、度量原则。这些原则在会话场景与代码场景中完全同构——探针方法论不因被测对象不同而改变。

#### 18.1　有效性原则

不可伪装性：探针必须触及模型无法通过运行时配置修改的层面，优先下沉到结构级（L3-L5 层）。核心证据不能来自自我声明和对话风格，否则伪装成本为零。在代码场景中，结构级探针检查哈希链、常量签名、LOCKED 引用——这些是模型无法通过「写更好的代码」来绕过的。

可区分性：探针的观测维度必须在不同目标之间产生统计显著分离。优先选择多参数联合命中的维度——单个特征可能是巧合，一组特征的联合模式就是签名。在代码场景中，异常处理模式 + 状态副作用模式 + 分层结构的联合模式构成模型的代码方言指纹。

可复现性：同一探针在不同时间、不同会话下执行，必须得到一致结果。工程上要固定温度、top_p、seed 等参数，输入做 Unicode 归一化，消除随机性干扰。在代码场景中，AST 解析是确定性的——同一代码输入永远产生同一 AST，探针结果可复现。

独立性：多条探针必须覆盖不同技术层，避免共因失效。十条全测对话风格的探针，不如一条架构级探针有分量——前者改一个系统提示就能全部骗过，后者要改就得重写整个组件。

#### 18.2　结构性原则

布尔化输出：裁决路径上的探针，输出必须是明确的 PASS/FAIL + 证据位置，禁止模糊的概率值。概率输出可被操纵，布尔结果没有中间地带。置信度、漂移趋势这类统计量，降级为调度信号，不参与最终裁决。

路径敏感性：探针必须绑定执行路径上下文。同一个变量在不同分支里的语义和约束完全不同，单一全局探针要么过严要么过松。正确的设计是：探针 = 检测逻辑 × 路径谓词。在代码场景中，同一变量在不同模块/不同层中的约束不同，探针按路径分。

覆盖诚实：每条探针必须显式声明自己的漏报面，禁止声称「全覆盖」。不存在没有盲区的探针，已知边界的探针远比虚假的「无风险」更安全。

版本绑定：每条探针携带版本号，所有裁决记录标注探针版本。探针升级后，结构级证据追溯重审，语义级证据仅向前生效，行为级证据重置统计窗口，避免版本漂移导致结论静默失效。

#### 18.3　工程化原则

最小扰动性：探针执行不能改变被测系统的状态。审计本身必须是无副作用的观测，不能触发模型的学习/适配机制，不能写入任何数据。在代码场景中，AST 解析是只读的，不修改代码。

单向依赖：探针读取上游数据，输出下游结果，禁止反向筛选输入。防的是结果导向的数据操纵——一旦允许「为了结论挑输入」，审计的客观性直接归零。

#### 18.4　三条元原则

所有具体原则，最终都收敛为三条：第一，审计的是行为，不是表态。第二，确定性做裁决，统计性做信号。第三，探针的强度不在覆盖多广，而在漏报面是否已知且受控。

### 第十九章　PTH 锚点契约模板

PTH（Project Truth Hierarchy）锚点契约是项目全局行为契约，写成机器可读、可被探针审计的规范。它相当于项目内部的「法律」，所有模型生成代码必须遵守。以下是 PTH 锚点契约模板的核心条目：

【PTH 锚点契约模板】

# 1. 异常统一策略
- 禁止裸吞异常（try-catch 不打日志直接吞）
- 所有业务异常必须抛出项目自定义异常枚举（如 OrderException）
- 禁止使用 Result<T> 包装替代异常抛出（项目统一异常策略）

# 2. 状态契约
- 所有传入函数的对象，函数不得修改（immutable 入参）
- 如需修改必须返回新副本（copy-on-write）
- 全局状态禁止直接修改，必须通过 setter 方法

# 3. 分层契约
- Controller 只能参数校验 + 转发逻辑，禁止任何业务计算
- Service 层禁止直接操作数据库连接
- DAO 层禁止包含业务逻辑

# 4. 资源契约
- 所有打开的句柄（文件/连接/流）必须在同函数 finally 关闭
- 线程池必须在应用关闭时优雅停机
- 数据库事务边界在 Service 层

# 5. 日志契约
- 所有错误路径必须打印 error 日志 + 唯一错误码
- 禁止使用 System.out.println 替代日志
- 敏感信息禁止打印日志

# 6. 接口契约
- 所有跨模块调用必须通过 LOCKED 接口
- 禁止直接 import 其他模块的内部实现
- 接口变更必须重新分配 πₛ 并重新审计

检测内核仍是 AST 遍历 + 规则匹配（成熟技术栈，如 JavaParser、tree-sitter）。账本是一条追加式哈希链 + 一个 π 分配器（O(1) 追加，O(n) 验证）。验签是一次数字签名校验（RSA/ECDSA，毫秒级）。全部是工程设施级组件，没有任何一处需要理解代码全语义——方舟级的深渊（全语义翻译）依然不存在。

真正的增量成本在治理流程的纪律性，而那本来就是 PEF-CIC 的架构哲学。具体而言：每个模块产出后必须过 M-E-F 全链路（而非直接合并），这增加了流程时间，但消除了方言偏差。D-S 指纹库的维护是统计性的，不增加单轮裁决延迟。

五个盲区: 接口篡改/审计者自审/无漂移统计/契约篡改/先合了再说。

五种设施: πₛ绑定/π分域/D-S指纹库/常量验签/LOCKED+降级域。

全景图: 三形态共享核心架构，形态一三完整部署，形态二探针外借。

## 第八部分　应用场景边界

### 第二十四章　三种形态的适用边界

PEF-CIC + π 锚点体系的三种形态各有适用边界，不能混用：

形态三（多模型代码接力）的适用边界：第一，必须有 PTH 锚点契约先行——没有契约，探针无审计目标。第二，模块边界必须清晰可拆——无法拆分的单体代码不适合多模型接力。第三，跨模型引用必须通过 LOCKED 接口——直接 import 内部实现会被结构级探针 FAIL。第四，整合节点（Trae）必须接受被审地位——如果整合节点拒绝被审计，架构无法闭环。

### 第二十五章　与方舟编译器的本质区别

用户曾问：这层翻译器是否会很复杂，类似华为的方舟编译器一样？答案是：本质区别，不类似。

方舟编译器的核心任务是「全语义翻译」——将一种语言的代码完全理解，翻译成另一种语言的可执行代码。这需要类型推导、控制流分析、数据流分析等编译器级技术，复杂度极高。PEF-CIC 跨模型治理的核心任务是「契约审计」——用 AST 解析检查代码是否符合 PTH 锚点契约，输出 PASS/FAIL。这不需要理解代码的全语义，只需要模式匹配（如「是否有裸 try-catch」「是否修改了入参」），复杂度是 Linter 级（如 ESLint、Checkstyle），是成熟技术栈。

关键结论：PEF-CIC 不是「翻译器」，而是「审计器」。它不翻译代码，只检测代码是否合规。方舟级的深渊（全语义翻译）在 PEF-CIC 中不存在——真正的增量成本在治理流程的纪律性，而非检测复杂度。

【公式闭环】第八部分 公式闭环

形态三边界: PTH 契约先行 + 模块可拆 + LOCKED 引用 + 整合节点被审。

与方舟区别: 方舟做全语义翻译（编译器级），PEF-CIC 做契约审计（Linter 级）。

复杂度: PEF-CIC 是 AST + 规则匹配，非全语义理解。

定位: 审计器非翻译器，输出 PASS/FAIL 非目标代码。

【PTH 锚点契约模板 v1.0】

# 1. 异常统一策略
- [P-EXC-001] 禁止裸吞异常：try-catch 块必须有日志或重新抛出
- [P-EXC-002] 所有业务异常必须抛出项目自定义异常枚举（如 OrderException）
- [P-EXC-003] 禁止使用 Result<T> 包装替代异常抛出
- [P-EXC-004] 异常信息必须包含上下文（orderId, userId 等）

# 2. 状态契约
- [P-STA-001] 所有传入函数的对象，函数不得修改（immutable 入参）
- [P-STA-002] 如需修改必须返回新副本（copy-on-write）
- [P-STA-003] 全局状态禁止直接修改，必须通过 setter 方法
- [P-STA-004] 缓存操作必须线程安全

# 3. 分层契约
- [P-LAY-001] Controller 只能参数校验 + 转发逻辑，禁止业务计算
- [P-LAY-002] Service 层禁止直接操作数据库连接
- [P-LAY-003] DAO 层禁止包含业务逻辑
- [P-LAY-004] 跨层引用禁止（Controller 不能直接调 DAO）

# 4. 资源契约
- [P-RES-001] 所有句柄（文件/连接/流）必须在 finally 关闭
- [P-RES-002] 线程池必须在应用关闭时优雅停机
- [P-RES-003] 数据库事务边界在 Service 层
- [P-RES-004] HTTP 连接必须设置超时

# 5. 日志契约
- [P-LOG-001] 所有错误路径必须打印 error 日志 + 唯一错误码
- [P-LOG-002] 禁止 System.out.println 替代日志
- [P-LOG-003] 敏感信息禁止打印日志
- [P-LOG-004] 关键业务操作必须打印 info 日志

# 6. 接口契约
- [P-INT-001] 所有跨模块调用必须通过 LOCKED 接口
- [P-INT-002] 禁止直接 import 其他模块的内部实现
- [P-INT-003] 接口变更必须重新分配 πₛ 并重新审计
- [P-INT-004] 接口参数必须携带类型注解

# 7. 命名契约
- [P-NAM-001] 类名 PascalCase，方法名 camelCase，常量 UPPER_SNAKE
- [P-NAM-002] 接口名不加 I 前缀（项目统一风格）
- [P-NAM-003] 包名全小写，禁止下划线

# 8. 测试契约
- [P-TST-001] 所有 Service 方法必须有单元测试
- [P-TST-002] 测试覆盖率 ≥ 80%
- [P-TST-003] 集成测试必须覆盖异常路径
